# LS-INVENTORY

Local-intranet inventory management system for electronic component reels ("LS Technology"). Tracks items → reels (physical stock units) → boxes (groups of reels), inward (receiving) and outward (shipping) movements, an approval workflow for non-admin staff, a purchase-order/mini-CRM module, a **Reports** section (formerly "Dashboard", renamed and split into a sidebar of sections — Stock Summary, Search & Trace, Analytics, Dead & Low Stock, and a new Daily Report with PDF export, see §4/§6a), and QR-coded label/packing-list PDF generation. Stock is now tracked per **store** — "LS Tech Stores" (primary) and "Gelco Stores" (secondary) — with a Stock Transfer feature to move reels/boxes between them (see the multi-store note in §2 and the new `routes/transfer.js` in §4). Two Gelco-specific roles (`gelco_manager`, `gelco_worker`) are permanently locked to Gelco Stores only, gated behind a daily "approve yesterday's outward summary" ritual (§3); there's also an admin/manager-only Notifications page (every outward event, date-filterable) and a "Docs" tab (`/gelco-docs`, labeled "Docs" in the nav) for uploading PO/Invoice PDFs to Cloudflare R2, with its list content filtered by the top-right store-view dropdown (§4, §6). Nav brand text is "LS INV MGT".

## 1. Tech stack

- **Runtime**: Node.js >= 20.9 (raised from >=18 — Next.js 16 requires it; `package.json`'s `engines` and a root `.node-version` both pin it, since a Render deploy running Node 18 previously failed silently on the frontend half), plain CommonJS, no bundler/build step.
- **Web framework**: Express 4.
- **Templating**: none server-side. `server.js` used to `res.sendFile()` static HTML from `views/`; as of the Next.js migration (§6a) it instead reverse-proxies every page to a separate Next.js process. Either way, all dynamic behavior is client-side `fetch` against `/api/*` (no SSR data-fetching anywhere).
- **Database**: SQLite via `@libsql/client` — local file `./inventory.db` by default, or Turso (managed libSQL cloud) when `TURSO_URL` is set.
- **Auth**: `jsonwebtoken` (JWT, 30-day expiry, stored as a `token` cookie or `Authorization: Bearer` header) + `bcrypt` password hashing + `cookie-parser`.
- **PDF**: `pdfkit`. **QR codes**: `qrcode`. **Logging**: `morgan('dev')`. **Env**: `dotenv`. **File upload**: `multer` (memory storage) + `@aws-sdk/client-s3` (Cloudflare R2, Gelco Docs tab only — same versions/pattern as the sibling `ls_crm` app).
- **Frontend**: **migrated to Next.js 16 (App Router) + Tailwind v4 + shadcn/ui, in a separate `frontend/` app — see §6a, the current source of truth for the frontend.** The legacy `public/js/app.js`, `public/css/style.css`, and every `views/*.html` file were deleted in the legacy-cleanup commit once the migration had been stable for a while (§6a) — see git history before that commit if you need to reference the old vanilla-JS/HTML implementation. CDN libs from the legacy frontend (Chart.js 4.4.0, html5-qrcode 2.3.8) are now regular npm dependencies of `frontend/`, not CDN `<script>` tags.
- No TypeScript, no ORM, no test framework on the backend — raw SQL strings throughout. `frontend/` does use TypeScript (shadcn CLI convention).
- Root `package.json` scripts: `start` → runs `node server.js` and the built Next.js app together via `concurrently -k` (§6a); `build` → builds `frontend/`; `dev` → `node --watch server.js` (Express only — run `npm run dev:next` in another terminal for the Next.js dev server); `dev:next` → `next dev` in `frontend/`.

## 2. Database schema

Created idempotently by `initDB()` in [db/schema.js](db/schema.js) on every startup (`CREATE TABLE IF NOT EXISTS`).

**items** — `id` PK, `item_code` TEXT UNIQUE, `description` TEXT, `default_spq` INTEGER (default 1), `status` TEXT (default `'active'`; `'Deleted'` = soft-deleted; added via a best-effort `ALTER TABLE` migration for pre-existing DBs), `created_at`.

**boxes** — `id` PK, `box_number` TEXT UNIQUE (`BOX-####`), `item_code` TEXT, `reel_count` INTEGER, `created_at`.

**reels** — `id` PK, `reel_number` TEXT UNIQUE (`REEL-#####`), `item_code` TEXT, `box_number` TEXT (nullable), `quantity` INTEGER, `status` TEXT (default `'In Stock'`; also `'Outwarded'`, `'Deleted'`), `inward_date`, `notes` TEXT (free-text "batch" label, printed on labels).

**outwards** — `id` PK, `reel_number` TEXT, `customer_name` TEXT, `invoice_number` TEXT, `quantity_shipped` INTEGER, `outward_type` TEXT (default `'Full'`, or `'Partial'`), `outward_date`, `notes` TEXT, `store_code` TEXT (default `'primary'`, added — see multi-store note below), `company_id`/`po_id` INTEGER (nullable FKs into `crm_companies`/`crm_purchase_orders` — see the shared-DB note below; added via the same best-effort `ALTER TABLE` pattern, closing a gap where `utils/inventory.js`'s `executeOutwardReel` inserted these but `initDB()` never created them, so a genuinely fresh local DB couldn't run `/api/outward/grouped` at all).

**counters** — `name` TEXT PK, `value` INTEGER (default 10000). Seeded rows: `('reel', 10000)`, `('box', 1000)`. ⚠️ `routes/po.js` also reads/increments a `'po_sys'` row (`nextSysPONumber()`), but `initDB()` never seeds it — no insert-if-missing guard like `reel`/`box` have. **Reel/box numbering is a single global sequence across all stores** — there is no per-store counter, by design (see multi-store note below).

**requests** — `id` PK, `type` (`'inward'`|`'outward'`|`'transfer'`), `status` (default `'pending'`; also `'approved'`|`'rejected'`), `created_by` TEXT (username), `created_at`, `reviewed_by`, `reviewed_at`, `reject_reason`, `payload` TEXT (JSON blob of the original request body — for `inward`/`outward` this now also carries `store_code`; for `transfer` it carries `{kind, number, to_store, notes}`).

**users** — `id` PK, `username` TEXT UNIQUE, `password` TEXT (bcrypt hash), `role` TEXT (default `'user'`; also `'admin'`, `'manager'`, `'client'`, `'gelco_manager'`, `'gelco_worker'` — the last two added, see §3), `created_at`. Seeded (only if the table is empty) with **plaintext** passwords: `admin/admin123` (admin), `pranav/lstech123` (manager), `zakir/lstech123` (user), `sahil/lstech123` (user) — see §5 for why this matters.

### Multi-store support (added)

**stores** — `id` PK, `code` TEXT UNIQUE, `name` TEXT, `active` INTEGER (default 1), `created_at`. Seeded idempotently: `('primary', 'LS Tech Stores')`, `('secondary', 'Gelco Stores')`. `GET /api/stores` returns active stores; this is the source of truth for every store dropdown in the UI — adding a third store later is a single `INSERT`, no code changes needed for the store list itself (routes/UI that filter by store still need touching, per §4).

**stock_transfers** — `id` PK, `reel_number` TEXT (nullable), `box_number` TEXT (nullable), `from_store`, `to_store`, `quantity` INTEGER, `transferred_by` TEXT (username of the original requester, not the approver), `transferred_at`, `notes`, `status` (default `'completed'`, unused beyond that default today). Log of every transfer, written by `executeStockTransfer()`. **One row per reel moved, always** — a box transfer of N reels logs N rows (each with both `reel_number` and `box_number` set), not one row with a summed quantity; this is what makes undo precise per-reel instead of reverting "whatever's currently in the box" (§4/§5). A pre-change *box*-kind transfer would have logged one row with `box_number` set, `reel_number` NULL, and a pre-summed quantity — `routes/transfer.js`'s undo keeps a legacy fallback for that exact shape, since no new rows are ever created that way. In practice no such row currently exists in production (the one real transfer so far, by `pranav`, was an individual-reel transfer — `reel_number` set, `box_number` null, unaffected by any of this either way); the fallback is defensive, not dead code covering a real row today.

`reels`, `boxes`, and `outwards` all gained a `store_code TEXT NOT NULL DEFAULT 'primary'` column via the same best-effort `ALTER TABLE ... ADD COLUMN` + try/catch pattern already used for `items.status` — every pre-existing row silently became `'primary'` stock with zero backfill. New indexes: `idx_outwards_date`, `idx_reels_inward_date`, `idx_reels_store`, `idx_boxes_store`. `items` (the catalog) deliberately stays store-agnostic — it's a shared SKU list, not physical stock — but Catalog and most of Reports still filter by the selected store, *derived* from `reels` at query time rather than stored on `items` (see `routes/items.js` in §4).

⚠️ **This schema migration is live on the production Turso DB** (applied 2026-08-29, verified via a full table dump — see `scripts/backup-db.js` below — zero data loss: all 5,256 pre-existing reels confirmed `store_code='primary'`). The application code that uses these columns (routes, UI) is deployed too now — multi-store filtering across Dashboard/Inward/Outward/Transfer/Notifications/Settings/Gelco Docs, previously the pending half of this migration, shipped this session.

### Gelco roles, daily gate, and Gelco Docs (added)

**daily_gate_approvals** — `id` PK, `store_code` TEXT, `gate_date` TEXT (`'YYYY-MM-DD'`, IST calendar day), `approved_by` TEXT, `approved_at`, `UNIQUE(store_code, gate_date)`. One row per store per day once a Gelco Manager approves that day's gate (see §3) — plain `CREATE TABLE IF NOT EXISTS`, brand new table.

**gelco_docs** — `id` PK, `doc_type` TEXT (`'po'`|`'invoice'`), `original_filename` TEXT, `file_url` TEXT (public Cloudflare R2 URL — the file bytes themselves are never stored in this DB), `uploaded_by` TEXT, `uploaded_at`, `store_code` TEXT (default `'secondary'`, added via the same best-effort `ALTER TABLE` pattern — every upload today is tagged `'secondary'` since this feature only serves Gelco's paperwork, but the column lets the "Docs" tab's list genuinely filter by the top-right store dropdown rather than always showing everything). Backs the "Docs" nav tab (labeled "Docs", route still `/gelco-docs` — see §4, §6) — a deliberately simple PDF-upload log, not a real `crm_invoices`/Tally integration (that has zero application code anywhere in this repo and was explicitly out of scope for this round of work). Table itself is named `gelco_docs` (not a generic `docs`) so its scope/ownership is unambiguous if other stores ever get their own doc storage later — a plain `docs` table briefly existed under the old name before this rename and was dropped (confirmed empty first).

`db/schema.js` also exports `istDateString(d)` and `istDayBounds(dateStr)` next to `nowIST()` — these compute "today"/"yesterday" and day-start/day-end bounds using the same `+5.5h` offset arithmetic `nowIST()` already uses. **Never use SQLite's `date('now', ...)` for day-boundary logic in this codebase** — it's UTC-based, while every stored timestamp here is a naive IST-wall-clock string; using SQLite's `date()` for "yesterday" would be wrong by ~5.5 hours right around midnight IST.

### Tables referenced in code but not created by `initDB()` — because this app doesn't own them

`routes/po.js` reads/writes `crm_companies`, `crm_contacts`, `crm_purchase_orders`, `crm_po_items`, `crm_tasks`. **Confirmed via a read-only live query against the actual Turso DB** (`SELECT sql FROM sqlite_master WHERE name LIKE 'crm_%'`): this app's `TURSO_URL` points to the **same physical database as the sibling `ls_crm` app** — the shared DB also has tables with zero relevance to inventory (`crm_invoices`, `crm_tally_*`, `crm_bank_accounts`, `crm_products`, `crm_notes`). `ls_crm` owns these tables' schema and evolves it independently (visible in the live schema itself — `crm_contacts`/`crm_purchase_orders`'s stored `CREATE TABLE` statements carry extra columns appended after the original close-paren, the unmistakable signature of `ls_crm`'s own `ALTER TABLE ADD COLUMN` migrations accumulating over time, the same idiom this repo uses for its own columns). Deliberately **not** creating these 5 tables here — doing so (even as a harmless `IF NOT EXISTS` no-op against the shared DB) would make `db/schema.js` a second, drifting source of truth for tables another app owns. Instead, `initDB()` runs a startup existence check (one `sqlite_master` query for all 5 names) and `console.warn`s clearly, naming the missing tables and that they're `ls_crm`'s, if any aren't found — turns a confusing first-`/api/po/*`-request 500 into an immediate, legible startup signal instead. A genuinely fresh local DB still can't exercise PO features (no dedicated seed/fixture exists) — that stays the accepted status quo, just with a clear reason now instead of a silent one. There is also no dedicated frontend page for POs (no `po.html`/equivalent page.tsx); the only UI surface for this module is the customer/PO picker embedded inside the Outward page — and per a migration audit, 9 of `routes/po.js`'s 12 endpoints (create/edit/confirm/dispatch/cancel a PO) have *never* had any frontend, old or new, calling them; only `GET /companies`, `GET /companies/:companyId/open`, and `GET /:id` are ever called. Left as-is deliberately — likely intentional scaffolding for a future PO-management UI, not dead code to remove on a guess.

### Stale on-disk artifacts

`inventory.db` (local SQLite file, gitignored) is behind the current `db/schema.js` state at any given moment (it's regenerated fresh by `initDB()` on first run without `TURSO_URL`) — confirming the app runs against Turso in practice, this file is dev-only, not authoritative. `local_dump.sql` and `data_only.sql` (older, tracked SQL dump artifacts, same "not authoritative" category) were deleted once confirmed unreferenced anywhere in the repo. `192.168.1.50+2.pem`/`-key.pem` (mkcert-style TLS files) sit in the repo root but are never referenced by `server.js` (HTTP only) — still a leftover, deliberately not deleted (§6a backlog #2 — needs a security decision, not a code-cleanup pass).

## 3. Auth & roles

- **Login**: `POST /api/login` looks up the user, `bcrypt.compare`s the password, signs a JWT `{id, username, role}` with `SESSION_SECRET` (30-day expiry). The client stores the returned token as a `document.cookie` (`SameSite=Strict`, not httpOnly — set by JS, so any page script can read it).
- **`requireLogin` middleware** ([server.js](server.js)): reads `Authorization: Bearer <token>` or the `token` cookie, verifies the JWT, sets `req.user`. Unauthenticated `/api/*` → 401 JSON; other paths → redirect to `/login`.
- **Roles**: `admin`/`manager` are "approver" roles — their inward/outward actions execute immediately, and they can approve/reject/edit-approve pending requests, manage users, and cancel POs. `user` (staff) actions are queued into `requests` pending approval. `client` is redirected to `/stock` for any non-API, non-`/public` **page** path. `gelco_manager` and `gelco_worker` (added — see below) are permanently locked to Gelco Stores only.
- **`client` role is now API-enforced, not just UI-hidden.** ~~Previously~~: the page-redirect middleware in `server.js` explicitly excludes `/api/*`, so a `client`-role JWT could call almost the entire API directly (curl/Postman/etc.), not just the one endpoint `/stock` (the only page `client` can reach) actually calls (`GET /api/dashboard/stock-summary`). Fixed with one allowlist middleware in `server.js` (`CLIENT_API_ALLOWLIST`, mounted right after the page-redirect middleware, same exact-match style) rather than patching individual route files — `role === 'client'` now 403s on every `/api/*` path except `/api/auth/me`, `/api/stores`, and `/api/dashboard/stock-summary`. Verified exhaustively (not spot-checked) against all ~60 endpoints across every route file with a throwaway test `client` account. The old per-file `role === 'client'` checks in `routes/outward.js`'s `POST /grouped` and `routes/transfer.js` are now redundant (the allowlist middleware blocks `client` before they'd ever run) but left in place — harmless belt-and-suspenders, not worth the diff to remove. **This gap was deliberately NOT extended to the two new Gelco roles** — see below, every one of their restrictions is enforced server-side (and always was).

### Gelco roles (added)

`gelco_manager` and `gelco_worker` exist only to run the Gelco Stores side of the business, with every restriction enforced server-side (not just hidden in the UI, unlike the `client`-role gap above):

- **Page access — allowlist, not blocklist**: `server.js`'s page-redirect middleware (previously a single hardcoded `client`→`/stock` check) is now a `ROLE_PAGE_ALLOWLIST` map: `client` → `['/stock']` (unchanged), `gelco_worker` → `['/outward']` (narrowed from `['/inward', '/outward']` — Inward removed, per request), `gelco_manager` → `['/', '/outward', '/gelco-docs']` (narrowed from also including `/inward`/`/transfer`/`/requests`). Anything not in a role's list redirects to `/outward` (was `/inward` for both, before the narrowing) or `/stock` for `client`. An allowlist means any future new page is safe-by-default for these two roles without remembering to add it to a blocklist. Mirrored client-side in `frontend/lib/role-allowlist.ts`'s own `ROLE_PAGE_ALLOWLIST` (UI-only, `server.js` is the real boundary) — a `getVisibleNavLinks()` helper in `frontend/lib/nav-links.ts` uses it to decide what `Nav.tsx`/`BottomNav.tsx` render, and also appends a "Docs" link (gated by a separate `GELCO_DOCS_ROLES` constant: `admin`/`manager`/`gelco_manager`) that isn't part of the regular per-role page list.
- **`routes/dashboard.js` blocks both Gelco roles outright** (`403` on every route via a `router.use(...)` guard) — the page is already unreachable per the allowlist, but the API routes themselves have no other role gating, so this closes what would otherwise be a direct route to full cross-store business data (customers, revenue-shaped quantities, dead stock) that defeats "Gelco Stores only."
- **`routes/po.js` is deliberately NOT blocked for Gelco roles** — both have the Outward tab, and `outward.html`'s shipment flow requires `GET /api/po/companies` (customer autocomplete) and the PO picker to populate a valid `company_id` before a cart can submit, exactly like `admin`/`manager`/`user` today. Blocking `po.js` here would silently break Outward for both roles.
- **Store is forced server-side, not just defaulted**: `routes/inward.js` `POST /`, `routes/outward.js` `POST /`/`POST /box`/`POST /grouped`, and `routes/transfer.js` `POST /` all check `GELCO_ROLES.includes(req.user.role)` (a `['gelco_manager', 'gelco_worker']` array defined per-file) and force `store_code = 'secondary'`, overriding whatever the client sent. `outward.js`'s three write paths additionally verify the reel's/box's *actual current* `store_code === 'secondary'` before proceeding (`403` otherwise) — without this, a Gelco user could outward a Primary-store reel while the transaction gets mislabeled `store_code='secondary'`, corrupting store attribution. `transfer.js`'s `POST /` requires the transfer to involve Gelco on at least one side (`to_store === 'secondary'` or the looked-up current store is `'secondary'`) — `403` otherwise, so Gelco roles can't use Transfer to move unrelated Primary↔Primary stock. `GET /recent` on all three route files forces `store='secondary'` server-side for these roles regardless of any `?store=` query param.
- **Approval model — reworked so the daily gate is the only review step, not per-request approval**: `gelco_manager` is still an approver (`APPROVER_ROLES` in `inward.js`/`outward.js`/`transfer.js`/`requests.js` all still include it, so their own actions execute immediately), but they no longer have any UI path to `/requests` — it was removed from their page allowlist above specifically so the daily gate (below) is their sole review mechanism, not individual pending-request approval. The `isGelcoRelevant`-scoped `GET /`/`GET /count`/`POST /:id/approve`/`POST /:id/reject`/`POST /:id/edit-approve` logic in `requests.js` still exists and still works if called directly, but is effectively dormant for this role now that nothing links to it. `gelco_worker`'s Outward submissions used to queue as pending requests for exactly that now-unreachable approval step; instead, `routes/outward.js` has its own separate, file-scoped `APPROVER_ROLES` (deliberately not shared with `inward.js`/`transfer.js`/`requests.js`, whose own local copies stay `admin`/`manager`/`gelco_manager` only) that now also includes `gelco_worker`, so their Outward actions execute immediately — the daily gate below is the actual check on whether they can write at all, not this. `gelco_worker` still gets an explicit `403` on `GET /api/requests` and `GET /count` (not an approver anywhere else) — the pre-existing `user`/`client` exposure on these same endpoints is a separate, un-touched gap.
- **Daily gate**: `gelco_manager`/`gelco_worker` must clear a daily "approve yesterday's Gelco outward summary" gate before they can write anything — for this role pair, this is now the *entire* review workflow, not a supplementary check alongside per-request approval (see above). See `routes/daily-gate.js` in §4 and `utils/dailyGate.js` in §5 for the mechanism; enforced both as a frontend blocking overlay (`frontend/components/layout/DailyGateOverlay.tsx` + `frontend/hooks/use-daily-gate.ts`) and as a real server-side backstop on the same write endpoints listed above (`isGateApprovedToday('secondary')` checked before any mutation). `admin`/`manager` are exempt (always read as approved).
- **Role validation**: `routes/settings.js`'s `validRoles` allowlist (the only role-value validation in the codebase, `POST /users`) now includes `gelco_manager`/`gelco_worker`; `PUT /users/:id` previously had **no role validation at all** — this was closed at the same time (now shares the same allowlist check), a pre-existing gap unrelated to the new roles.
- **Gotchas**:
  - Default seeded users have **plaintext** passwords in the DB — `scripts/hashpasswords.js` must be run once after first seed, or login will fail (`bcrypt.compare` can't match a plaintext string).
  - `SESSION_SECRET` falls back to the literal string `'fallback-secret'` if unset in `.env`.
  - A **hardcoded password `'admin123'`** (not env-configurable) gates the remaining undo/delete endpoints: `POST /api/inward/undo`, `POST /api/dashboard/delete`. **Also role-gated** (`admin`/`manager` only, checked before the password) — closes the gap where any logged-in role who had/found the password string could use them regardless of role. This is *hardening*, not a fix for the underlying mechanism: the password itself is still one shared string, not user-specific, not rotatable without a code deploy — that stays open as its own deferred item (§9). `POST /api/transfer/undo` and `POST /api/outward/undo` both used to carry this same password check too — dropped from both by request, so they're role-gated only now (`admin`/`manager`), no password.
  - No session store / revocation — `GET /api/logout` only clears the client cookie; a copied token stays valid for the full 30 days.
- `scripts/adduser.js` — interactive CLI to create a properly-hashed user. `scripts/hashpasswords.js` — one-off migration that hashes any password not already starting with `$2b$`.

## 4. Routes

### `server.js` (top level)
- `GET /login` — public, serves `views/login.html`.
- `POST /api/login`, `GET /api/logout` — see §3.
- `GET /`, `/inward`, `/outward`, `/transfer`, `/reports`, `/reports/search`, `/reports/analytics`, `/reports/alerts`, `/reports/daily`, `/requests`, `/stock`, `/settings`, `/notifications`, `/gelco-docs` — serve the matching static page from `views/`. `/reports` (formerly `/dashboard`) is a sidebar with 4 sub-routes now, each needing its own exact-match entry in `MIGRATED_PAGE_PATHS` per §6a's exact-match-only proxy rule. Page access for `client`/`gelco_manager`/`gelco_worker` is gated by the `ROLE_PAGE_ALLOWLIST` map described in §3.
- `GET /api/auth/me` — `{username, role}` from the JWT, used for role-aware nav UI.
- `GET /api/stores` — `[{code, name}]` of active stores, no role gating beyond login. Backs every store dropdown in the UI.
- Mounts: `/api/items`, `/api/inward`, `/api/outward`, `/api/requests`, `/api/settings`, `/api/dashboard`, `/api/po`, `/api/labels`, `/api/transfer`, `/api/daily-gate`, `/api/gelco-docs`.
- `CLIENT_API_ALLOWLIST` middleware (mounted right after the `ROLE_PAGE_ALLOWLIST` page-redirect middleware, before the route mounts above) — for `role === 'client'` only, 403s any `/api/*` path not in `['/api/auth/me', '/api/stores', '/api/dashboard/stock-summary']`. See §3 for why this exists (closes the API-level gap the page redirect alone never covered).
- Prints local + LAN IPv4 URLs on startup (designed to be reached from warehouse phones/scanners on the same network). If `RENDER_SERVICE_URL` is set, self-pings every 14 minutes (Render.com free-tier anti-sleep hack).

### `routes/items.js` → `/api/items` (catalog CRUD, no role gating beyond login; all handlers wrapped in `ah()` — previously unwrapped, see §9)
- `GET /?store` — active items, newest first. `store` (new) is a *derived* filter, not a stored one: when set to a real store code (not `'all'`/omitted), adds `AND EXISTS (SELECT 1 FROM reels r WHERE r.item_code = items.item_code AND r.store_code = ? AND r.status = 'In Stock')` — an item only appears for a store if it currently has live stock there. Deliberately not a column on `items` (§2's "items stays store-agnostic" still holds) — an item can have stock in multiple stores at once, so a static per-item store field would be the wrong model; this derives membership from `reels` at query time instead, so it's never stale. `GET /:itemCode` — one item (404 if missing).
- `POST /` — create; code trimmed+uppercased; if a `Deleted` item with the same code exists, restores it instead of erroring; 409 on non-deleted duplicate.
- `PUT /:itemCode` — update/rename (409 if new code taken, 404 if missing).
- `DELETE /:itemCode` — soft-delete (`status = 'Deleted'`); 400 if already archived.

### `routes/inward.js` → `/api/inward`
- `POST /` — `{item_code, num_reels, num_boxes, notes, store_code}`. `store_code` defaults to `'primary'` if omitted. Approver roles → `executeInward()` runs immediately; others → pending `requests` row (`type='inward'`, payload carries `store_code`). UNIQUE collisions → 409.
- `GET /recent?limit&offset&store` — paginated recent reels, newest first; `store` optionally filters by `store_code` (omit or `'all'` for every store). Still returns a bare array (unlike outward's `/recent`, see below).
- `POST /undo` — `{reel_numbers, password}`; requires `admin`/`manager` role (added — was previously password-only, so any logged-in role who had the password could use this) **and** password `'admin123'`; soft-deletes reels not already Outwarded; deletes any box left with zero non-Deleted reels.
- All handlers now wrapped in `utils/asyncHandler.js`'s `ah()` (previously unwrapped — see §9).

### `routes/outward.js` → `/api/outward`
- `GET /reel/:reelNumber` — reel + item description (400 if already Outwarded/Deleted). **Not store-filtered for the general store-view dropdown** — a scanned reel must resolve regardless of which store the nav dropdown happens to be viewing. `gelco_manager`/`gelco_worker` are the one exception: their lock to Gelco Stores isn't a view filter, it's a hard restriction, so this now `403`s (`Reel not available at Gelco Stores`) if the reel's `store_code !== 'secondary'` for those two roles — added so a Gelco scan is rejected at lookup time, not just at submit time (`POST /grouped` already had this same reel-level check, see below).
- `GET /box/:boxNumber` — box + its reels + in-stock/outwarded summary. Still not store-filtered server-side (a box can have reels split across stores, same as Transfer — see §4/§5's Transfer notes). The Outward frontend does the Gelco filtering itself using each reel's own `store_code` in the response: a Gelco box scan adds only reels at `secondary` to the cart and skips the rest into the visible skip list (reason `"Not at Gelco Stores"`, alongside the existing `"Already outwarded"`).
- `GET /recent?limit&offset&store&date_from&date_to&q` — **response shape is now `{rows, total}`**, not a bare array (changed for real server-side pagination — previously the client always requested `?limit=500` and paginated in-browser). `store` optionally filters by `store_code`; `date_from`/`date_to` filter by `outward_date` using explicit `'YYYY-MM-DD 00:00:00'`/`'YYYY-MM-DD 23:59:59'` string bounds (never SQLite `date()` — see the IST note in §2/§5), added for the Notifications page and reused by the daily-gate summary logic's pattern. `q` (new) does the same free-text OR-match across `reel_number`/`item_code`/`box_number`/`customer_name`/`invoice_number` as `/search`'s own `q`, added for Notifications' search box. `store` is forced to `'secondary'` server-side for `gelco_manager`/`gelco_worker` regardless of the query param.
- `GET /for-reprint?customer_name&invoice_number` — returns every outward record matching a customer+invoice pair (used by the Outward page's packing-list reprint flow, which previously abused `?limit=500` on `/recent` for this and would have silently missed records past that cap).
- `POST /undo` — `{outward_id}`; requires `admin`/`manager` role (added, same reasoning as `inward.js` above); the hardcoded `'admin123'` password this used to also require was dropped by request (matching `transfer.js`'s `POST /undo`, see below) — role is now the only gate. Restores reel quantity/status, deletes the `outwards` row.
- `POST /grouped` — cart-style outward across multiple reels of one item in one shipment; body includes `company_id`/`po_id` (CRM tie-in) and `store_code`; blocks `role === 'client'` (403 — now redundant with `CLIENT_API_ALLOWLIST` in §3/server.js, kept anyway); validates all reels first (this is where the per-reel `isGelco && reel.store_code !== 'secondary'` → 403 check already lived, ahead of the `GET /reel`/`GET /box` lookup-time checks added above); approvers execute each (partial failures collected, only fails if *all* fail); others get one pending request. `customer_name`/`invoice_number` stay required at this endpoint for every role including Gelco — the frontend is what changed (below), not this validation. `store_code` from the body is **no longer trusted as what gets recorded** — see the `executeOutwardReel` fix below; it's now only used for the Gelco eligibility check and as informational metadata on a pending request's payload.
- ⚠️ **Real production incident, found and fixed**: an admin/manager shipped ordinary primary-store reels to a real CRM customer named "Gelco Electronics Pvt. Ltd." while the Outward page's Shipping Store dropdown was left on "Gelco Stores" (`secondary`) — likely carried over from the top-nav store-view filter, since the dropdown seeds from it on page load and nothing forced it back for non-Gelco roles. `POST /grouped` only ever validated the shipping store against the reel's actual store for `gelco_manager`/`gelco_worker`; for every other role it trusted the client-submitted `store_code` outright. Result: 28 real `outwards` rows recorded `store_code = 'secondary'` while the underlying reels never left `primary` (`reels.store_code` unchanged, zero matching `stock_transfers` rows) — a pure data-entry/labeling bug, unrelated to the actual Gelco-store outward feature (the customer's name just coincidentally contains "Gelco" too). This surfaced as two Reports screens visibly disagreeing: `GET /recent` here filters by the reel's *current* `store_code` (so these rows showed nowhere), while `utils/dailyReport.js`'s Daily Report filters by the *outward row's own* `store_code` (so the same rows showed up as Gelco activity there) — the discrepancy was a symptom of the write-time bug, not a separate read-side bug; once outward-store and reel-store can no longer diverge, every query that reads either field necessarily agrees (a reel's `store_code` is frozen forever once `Outwarded` — `executeStockTransfer` excludes outwarded reels from eligibility, so nothing can move it again after the fact). Fixed at the source: `executeOutwardReel` (see §5) no longer accepts a `store_code` override at all, from any caller. The 28 pre-existing mislabeled rows were corrected directly (`store_code` set back to match each row's `reels.store_code`, i.e. `'primary'`) — verified zero `outwards`/`reels` `store_code` mismatches remain anywhere in the table afterward.
- ⚠️ **`POST /` (single-reel) and `POST /box` (whole-box) were removed** — a migration audit traced every `POST` call in the current Outward page and found `submitCart()` is the only submission path, exclusively via `POST /grouped`; these two dedicated endpoints had zero callers, superseded when the Next.js rewrite consolidated everything into the cart/grouped flow but never removed from the backend. `executeOutwardReel()` in `utils/inventory.js` is untouched (still used by `/grouped` and by `routes/requests.js`'s approval flow, which calls it directly) and `GET /box/:boxNumber` is untouched (still used for box preview/lookup before adding reels to the cart) — only the two dead `router.post(...)` handlers came out.
- ⚠️ **Known gap, found during this audit, not yet fixed**: unlike `inward.js`/`transfer.js`/`items.js`/`settings.js`/`gelco-docs.js`, this file still has no `asyncHandler` wrapping at all — same class of issue as §9's known issue, just not in that list. Deliberately left alone here (wasn't part of the reviewed/approved fix scope) — worth folding in next time this file is touched.
- **Gelco outward skips the CRM customer/PO tie-in entirely (frontend-only change, by request)**: `frontend/app/(app)/outward/page.tsx` hides the Customer Name field (+ CRM autocomplete), the Purchase Order picker, and `POValidationPanel` for `gelco_manager`/`gelco_worker`, showing a read-only "Shipment Label" field (today's date/time, `lib/format.ts`'s new `nowISTString()`) in their place. On submit, `customer_name` is hardcoded to `"Gelco Stores"` and `invoice_number` is set to that same timestamp label — computed once per submission and reused across every item-code group in the cart (not regenerated per API call), so a multi-item Gelco shipment still shares one label for reprint/grouping purposes, exactly like a real invoice number would. `company_id`/`po_id` are sent as `null`. The backend endpoint itself is unchanged (see `POST /grouped` above) — it still requires non-empty `customer_name`/`invoice_number` for every role, the frontend just always supplies them now instead of asking Gelco users to type them.
- **Fixed a real `storeCode` race condition while making the above change** (pre-existing bug, not introduced by it): `loadStores()` only ever runs once, from a mount-only `useEffect`, and originally read `isGelco` from its own closure — captured on the very first render, before `useAuth()`'s `GET /api/auth/me` had resolved, so `isGelco` was almost always still `false` at that point. When the fetch inside `loadStores()` finally resolved, it would set `storeCode` to the primary/preferred store instead of forcing `'secondary'`, even though the Shipping Store `<select>` was correctly `disabled` (that binding reads the live `isGelco`, not the stale one) — so a Gelco user saw a disabled dropdown stuck on "LS Tech Stores" while a real submission would still have gone through fine (`storeCode` is forced server-side regardless, per §3). Fixed with an `isGelcoRef` that `loadStores()` reads instead of the stale closure, plus a small `useEffect(() => { if (isGelco) setStoreCode("secondary"); }, [isGelco])` as a second line of defense for the opposite ordering (auth resolving before the stores fetch). Verified live end-to-end as `gelco_worker`: secondary-store reel scan succeeds, primary-store reel scan `403`s at lookup time, a mixed-store box scan adds only the secondary reel and skips the other with the new reason, the Shipping Store `<select>` shows "Gelco Stores" (disabled), and a real submission recorded `customer_name = "Gelco Stores"` / `invoice_number` = the shared timestamp label, packing-list PDF included.

### `routes/transfer.js` → `/api/transfer` (Stock Transfer)
- `GET /reel/:reelNumber`, `GET /box/:boxNumber` — lookup for the transfer page's number field (same shape as the equivalent `outward.js` routes).
- `POST /` — `{kind: 'reel'|'box', number, to_store, notes}`. Blocks `role === 'client'` (403). Approver roles → `executeStockTransfer()` runs immediately; others → pending `requests` row (`type='transfer'`).
- `GET /recent?limit&offset&store` — `{rows, total}` from `stock_transfers`, newest first; `store` matches either `from_store` or `to_store`. Since box transfers now log one row per reel (§2), a box move shows as N rows here, not one collapsed row — deliberate, matches the underlying per-reel undo granularity.
- `POST /undo` — `{transfer_id}`; role check tightened from "just not client" to `admin`/`manager` only (matching the same hardening as `inward.js`/`outward.js`/`dashboard.js`), but **no password check** — unlike those three, the hardcoded `'admin123'` gate was deliberately dropped here by request, so role is the only boundary on this one endpoint. Always reverts the specific `reel_number` on the row being undone — correct for both individually-transferred and box-batch-transferred reels, since both shapes carry their own `reel_number` since the per-reel-logging change. Keeps a legacy fallback (revert every reel currently in the box) only for pre-change rows that have `box_number` with no `reel_number`.
- **A reel that belongs to a box can be transferred individually** — this was a hard `throw` before ("transfer the whole box instead") and was deliberately changed: it's now an explicit, accepted business rule that reels in the same box can end up in different stores as a result of legitimate individual transfers. `executeStockTransfer` no longer trusts `boxes.store_code` for eligibility at all — see §5.
- `POST /`'s Gelco-role eligibility gate (`GELCO_ROLES.includes(userRole)` → "Transfer must involve Gelco Stores") also stopped trusting `boxes.store_code` for a `kind:'box'` request — same reasoning as above, one layer up: it now derives "does this box involve secondary" from whether any of the box's *current* in-stock reels are actually at `secondary`, not the box's own possibly-stale cached value. Without this, a Gelco user could be wrongly 403'd moving a box back out of Gelco that had, in reality, fully arrived there via individual reel transfers while `boxes.store_code` never got updated to match (`executeStockTransfer` itself re-derives eligibility fresh regardless, so this is a permission-gate fix, not a data-integrity one).
- Frontend UI (`frontend/app/(app)/transfer/page.tsx`) is a scan-to-cart flow now, matching Outward's UX: a persistent scan input (+ camera scanner, + mobile FABs) keeps adding reels/boxes to an in-memory cart; From Store/To Store/Notes are set once per batch; submit loops the cart. A box only submits as one atomic `kind:'box'` call when the cart holds *every* currently-eligible reel of that box — anything less (including a box that can never be "complete" because some reels have already scattered elsewhere) submits as individual `kind:'reel'` calls per reel, which the backend now supports. Changing From Store while the cart has entries clears it (every eligibility check in the cart was built against the old value). Each submission response is checked for `pending` (the same non-approver-role queueing every other write in this app has, see `POST /` above) — a queued-for-approval unit is reported and cleared from the cart separately from an immediately-completed one, never lumped into the same "transferred" count.

## 5. Business logic

- **`utils/inventory.js`**:
  - `executeInward(item_code, num_reels, num_boxes, notes, store_code='primary')` — throws if item missing/archived. If `num_boxes` is 0, creates standalone reels (no box) each at `default_spq`. Otherwise distributes reels evenly across boxes (remainder to the first boxes), creating a `boxes` row + `reels` rows, all tagged with `store_code`. Returns `{boxes, reels}`.
  - `executeOutwardReel(reel_number, customer_name, invoice_number, outward_type, quantity_shipped, notes, company_id, po_id)` — throws if reel missing/already Outwarded. `Partial` requires `1 <= qty <= reel.quantity - 1` (can't ship the entire quantity as "partial"); `Full` ships everything. Inserts into `outwards` using **the reel's own current `store_code`, always** — `store_code` used to be an optional 9th parameter callers could override, which is what let a real production incident happen (see `routes/outward.js`'s notes below): an admin/manager's Shipping Store dropdown disagreed with where the scanned reels actually were (left on "Gelco Stores" from browsing, while shipping ordinary primary-store reels to a real CRM customer named "Gelco Electronics Pvt. Ltd." — a coincidental name collision with the internal `secondary` store), and nothing outside the `gelco_manager`/`gelco_worker` validation path ever checked the two agreed. Fixed by removing the parameter entirely — the function now always reads `reel.store_code` fresh, so an outward's recorded store can no longer diverge from the reel's real location for any role, present or future caller. All three call sites (`routes/outward.js`'s `POST /grouped`, `routes/requests.js`'s `POST /:id/approve` and `POST /:id/edit-approve`) updated to stop passing it. Updates the reel (`Full` → qty 0 + status Outwarded; `Partial` → qty reduced, stays In Stock).
  - `executeStockTransfer(kind, number, to_store, notes, transferred_by)` — `kind` is `'reel'` or `'box'`. Shared internal helper `transferOneReel(exec, reel, to_store, transferred_by, notes, box_number)` does one reel's move + its own `stock_transfers` row, used by both branches — this is what makes every reel-move independently logged and undoable, whether it happened alone or as part of a box batch. Its `UPDATE` is compare-and-swap (`WHERE store_code = <value just read>`), throwing "already moved" if `changes === 0` — the actual concurrency guarantee, not the earlier `SELECT`.
    - `kind: 'reel'` — throws if missing/Outwarded/Deleted or `to_store === from_store`. **Does not check box membership** — a reel currently in a box transfers on its own fine, keeping its `box_number` on the log row for context; this was a hard `throw` before ("transfer the whole box instead") and was deliberately removed as a real business-rule change (§4), not a bug fix. Reels in the same box can legitimately end up in different stores afterward.
    - `kind: 'box'` — reads the box's *currently in-stock* reels fresh (Outwarded/Deleted reels don't count, don't block). `boxes.store_code` is never trusted for eligibility, only as a denormalized cache updated after a successful move — eligibility is computed live as "do all active reels share one `store_code`, matching the expected source." Zero in-stock reels → rejected outright (no zero-quantity transfer is created). Split across stores (some reels already moved elsewhere) → throws, naming the split, so eligible reels get transferred individually instead. Homogeneous and valid → wrapped in a real `db.transaction()` (see below) — every reel's CAS-protected move plus the box's own `store_code` update commit together or not at all. Returns `{from_store, to_store, quantity, reelCount}`.
- **`db/schema.js` helpers**: `queryAll`/`queryOne`/`execute` wrap the libSQL client. `withTransaction(fn)` — new, wraps `@libsql/client`'s real `db.transaction('write')`/`.commit()`/`.rollback()`; `fn` receives a `(sql, params) => {changes}` function matching `execute()`'s own signature so callers can share helper code between transactional and non-transactional paths. Used only by `executeStockTransfer`'s box branch — nowhere else in this codebase uses real transactions, everything else is sequential best-effort `execute()` calls; keep it that way outside cases needing genuine all-or-nothing atomicity. `getNextReelNumber()`/`getNextBoxNumber()` self-heal — before incrementing, they raise the counter to `MAX(counter, max numeric suffix already in the table)`, protecting against manual DB edits or counter/table desync. `nowIST()` returns a naive `UTC+5:30` timestamp string used everywhere instead of SQLite's UTC `CURRENT_TIMESTAMP` — this is why `public/js/app.js`'s date formatters explicitly append `+05:30` when parsing timestamps from the API.
- **`utils/pdf.js`**: `fitFontSize()` shrinks font size in 0.5pt steps until text fits a given width, used to keep reel numbers/codes from overflowing the small labels.
- **`utils/qr.js`**: `stripPrefix()` strips `REEL-`/`BOX-` so the QR payload is just the numeric id. `generateQRBuffer()` (PNG buffer, used for PDFs) and `generateQRDataURL()` (base64 PNG) — the latter appears unused by any current route.
- **`utils/dailyGate.js`** (new) — `isGateApprovedToday(storeCode)`: one `queryOne` against `daily_gate_approvals` for `(storeCode, istDateString())`. Shared by `routes/daily-gate.js`'s `GET /status` and the write-endpoint gate checks in `inward.js`/`outward.js`/`transfer.js` (§3).

## 6a. Frontend — current (Next.js + Tailwind + shadcn/ui)

All 11 pages from §6 are migrated and live. This is a **reskin, not a redesign** — same information architecture, same API calls, same design tokens (colors/radius ported 1:1 from `public/css/style.css`) — rebuilt in React/Tailwind/shadcn instead of hand-rolled DOM. The one deliberate deviation from "reskin" is typography (see Design tokens below).

### Architecture

`frontend/` is a **separate, self-contained Next.js 16 (App Router) app** — its own `package.json`, its own `node_modules`, no monorepo tooling. It runs as its **own Node process** (`next dev -p 3001` in dev, `next start -p 3001` in prod) and is never reached directly by users — `server.js` stays the single public entry point (same LAN-IP printing, same `RENDER_SERVICE_URL` keep-alive ping as always) and reverse-proxies specific page paths to it.

- **The proxy — two distinct instances, not one mounted twice**: `server.js` builds `nextProxy` (`pathFilter` matches `/_next` + `/_next/*` plus everything in `MIGRATED_PAGE_PATHS`, now all 11 page paths + `/favicon.ico`; `ws: true`) and a separate, narrower `preAuthNextProxy` (`pathFilter` matches only `/_next`/`/_next/*`, `/login`, and `/favicon.ico`; no `ws`). `preAuthNextProxy` is mounted before `requireLogin` (so `/login` itself is reachable pre-auth); `nextProxy` is mounted after `requireLogin` **and** the `ROLE_PAGE_ALLOWLIST` middleware, so auth/role gating actually runs before any other page reaches Next. This used to be a single `nextProxy` instance mounted twice with the same broad filter — a real bug, since the pre-auth mount matched every migrated path (not just `/login`), silently intercepting and answering every page request before `requireLogin`/the allowlist ever ran, for every role including unauthenticated visitors. Found and fixed; now two instances with genuinely different filters. Neither is mounted per-path (`app.use('/transfer', nextProxy)`) — Express strips the mount prefix from `req.url` for `app.use(path, mw)`, which silently forwarded every migrated page to Next's `/` instead of the real path during the pilot. Exact-match `pathFilter`, mounted globally, avoids that class of bug entirely — including for the root path (`/`), which a naive prefix-based proxy would have to special-case to avoid swallowing every other route. Only `nextProxy` has `ws: true` — giving both instances `ws: true` double-subscribes the shared `httpServer`'s `'upgrade'` event, which corrupts every WebSocket frame (e.g. Next's HMR client) rather than just failing to connect; also found and fixed.
- **WebSocket upgrades**: `http-proxy-middleware`'s automatic upgrade detection only fires after an initial plain HTTP request on the same path — a fresh WS handshake (e.g. Next's HMR client hitting `/_next/hmr` cold) never gets one. `server.js` explicitly does `httpServer.on('upgrade', nextProxy.upgrade)` after `app.listen()` to cover this; without it, HMR silently never connects and (confirmed during the migration) can leave a page stuck mid-hydration, not just "no live-reload."
- **Dev-mode API calls**: `frontend/next.config.ts` proxies `/api/:path*` to `EXPRESS_ORIGIN` (default `localhost:3000`) via `rewrites()`, but only when `NODE_ENV !== 'production'` — in prod, the browser only ever talks to Express directly (same-origin, no rewrite needed).
- **Production process**: root `package.json`'s `"build"` script runs `npm --prefix frontend install && npm --prefix frontend run build`; `"start"` runs `concurrently -k "node server.js" "npm --prefix frontend run start"` — the `-k` (kill-others) means if either process dies, both exit, letting the platform's own restart policy (Render, in this app's case) recover both together rather than needing a second process manager like pm2.
- **Legacy files removed**: `views/*.html`, `public/js/app.js`, `public/css/style.css` — plus the `server.js` Express static mount and role-allowlist bypass clause that only existed to serve them — were deleted in a dedicated cleanup commit once the migration had been stable in production for a while (see `LEGACY_CLEANUP_PLAN.md`'s git history for the verification trail if this ever needs auditing). Rolling back an individual page now means restoring the relevant file(s) from git history, not just reverting a `MIGRATED_PAGE_PATHS` entry.

WHERE store_code = <value just read>`) closing a real concurrency gap: two near-simultaneous transfer requests for the same reel could previously both have succeeded. All of this was verified directly against the live DB before writing a line of frontend code — full-box atomic transfer, an individually-moved boxed reel succeeding where it used to throw, a since-scattered box correctly rejecting a whole-box attempt, an empty box being rejected outright, and a forced race (both reads seeing the same stale value) proving only one of two concurrent writes ever takes effect. The frontend rewrite itself was then verified live end-to-end through the actual UI too — scan-to-cart, a partial box correctly flagged amber and submitting as individual reel transfers, the resulting item appearing in *both* stores' Catalog/Stock Summary simultaneously (since it now had live stock in both, a real many-to-many case the `EXISTS`-membership filter from the Catalog work handles natively), and row-level Undo reverting only the one specific reel it targeted, leaving its box-mates that had moved separately untouched. On a subsequent accuracy pass through this documentation (checking that what got written down actually matches the code, not just re-reading the prose), two more real issues turned up and got fixed for real, not just documented around. First: `routes/transfer.js`'s `POST /` has its own Gelco-role eligibility gate, separate from `executeStockTransfer`'s own checks, and it was still deriving a box's store from `boxes.store_code` directly — the same stale-cache assumption fixed inside `executeStockTransfer`, just one layer up and missed the first time. Now derives it from whether the box's current in-stock reels are actually at `secondary`, closing a real (if narrow) case where a Gelco user could have been wrongly blocked from moving a box that had, in reality, fully arrived there via individual reel transfers. Second: the new cart's `submitCart()` never checked each submission response for the `pending` flag non-approver roles get back (the same request-queueing every other write in this app already has) — it would have reported a merely-*queued* transfer as already completed. Fixed to track and report pending vs. completed separately, both still clearing from the cart (queued is still "handled," just not yet moved).

**Gap-fixing pass** (a "find all gaps, then fix them properly" request, reviewed and corrected once mid-plan — see below): closed the `client`-role API gap with one allowlist middleware in `server.js` rather than patching individual files (§3/§4), verified exhaustively against all ~60 endpoints with a throwaway test account rather than spot-checked. Role-hardened the 4 password-only undo/delete endpoints (`inward.js`/`outward.js`/`dashboard.js`/`transfer.js`) to also require `admin`/`manager` — explicitly documented as hardening, not a fix for the underlying shared-password mechanism (§9). Wrapped the remaining 20 unprotected async handlers across `items.js`/`settings.js`/`gelco-docs.js`/`inward.js`/`transfer.js` in `asyncHandler` (`routes/outward.js` turned out to have the same gap but wasn't in the reviewed scope — flagged, not fixed, see its §4 entry). A migration audit (triggered by "is `server.js` still needed now that there's Next.js?") confirmed Express is the entire backend, not migration debris — Next.js has zero API routes of its own — but found `routes/outward.js`'s `POST /`/`POST /box` genuinely dead (superseded by the cart/`grouped` flow) and removed them, while leaving `routes/po.js`'s 9 never-used write endpoints alone (likely intentional scaffolding, not the same kind of dead code). Deleted 3 stale tracked files (`local_dump.sql`, `data_only.sql`, `LEGACY_CLEANUP_PLAN.md`) and the unused Geist Mono wiring (`--font-mono`/legacy `--font` in `globals.css`, the `GeistMono` import in `layout.tsx`). The `crm_*` table gap took a real correction mid-plan: a first draft proposed `CREATE TABLE IF NOT EXISTS` for the 5 tables `po.js` needs, reasoning it's a no-op against the live DB — reviewed and reversed, since it would make this repo a second source of truth for tables a live introspection query proved are actually owned by the sibling `ls_crm` app (same shared Turso DB). Replaced with a startup existence check that warns instead of silently 500ing (§2/§9). `outwards.company_id`/`po_id` (genuinely this app's own columns, unlike the `crm_*` tables) were added to `initDB()` for real. Every fix was verified live: the exhaustive client-role sweep, the undo/delete role check against both a blocked and an allowed account, the `crm_*` warning firing correctly against a fresh local DB and staying silent against the real one, a full live regression of the Outward page's cart→submit→reprint flow through the actual UI, and — because this pass touched auth middleware and schema — a real `npm run build && npm start` production-topology check (not just dev mode), all on throwaway QA data created and hard-deleted the same way as the Transfer test above.

## 7. Config / environment

From `.env`: `TURSO_URL`, `TURSO_AUTH_TOKEN` (Turso cloud DB — if unset, falls back to local `./inventory.db`), `SESSION_SECRET` (JWT signing key).
Optional, not in `.env`: `PORT` (default 3000), `RENDER_SERVICE_URL` (enables the 14-minute keep-alive self-ping).
**New, required for the Gelco Docs tab** (`routes/gelco-docs.js`): `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`, `R2_PUBLIC_DOMAIN_URL` — copied directly from the sibling `ls_crm` app's `.env` (same bucket, `ls-crm-storage`; see §4's `gelco-docs.js` note on the differing key prefix that keeps uploads from colliding). Without these set, `POST /api/gelco-docs/upload` fails with a clean `500` rather than crashing — confirmed safe to run the rest of the app without them configured.

## 8. Running locally

1. `npm install`
2. Ensure `.env` has `SESSION_SECRET` (and `TURSO_URL`/`TURSO_AUTH_TOKEN` for the cloud DB, or omit both to use local `inventory.db`).
3. `npm start` (or `npm run dev` for auto-restart via Node's `--watch`).
4. On startup, `initDB()` creates missing tables/columns and seeds default counters + default users if `users` is empty.
5. **Run once after first seed**: `node scripts/hashpasswords.js`, so the default plaintext-seeded passwords become bcrypt hashes (otherwise those accounts can't log in). Alternatively, use `node scripts/adduser.js` to create hashed users interactively from the start.
6. Visit `http://localhost:3000/login`. The server also logs LAN URLs for access from other devices on the same network.

## 9. Known issues (not yet fixed)

- **`routes/outward.js` has no `asyncHandler` coverage at all.** `items.js`/`settings.js`/`gelco-docs.js`/`inward.js`/`transfer.js` all had the same gap and are now fixed (wrapped in `ah()`, matching `po.js`/`dashboard.js`/`daily-gate.js`/`utils/pdf.js`) — `outward.js` was found to have the identical issue during that same pass but wasn't part of the reviewed/approved scope, so it was flagged rather than silently fixed. A handler here that throws won't crash the process (`server.js`'s `process.on('unhandledRejection', ...)` backstop prevents that) but the request just hangs instead of returning a clean error response.
- **The hardcoded `'admin123'` password on `inward.js`/`dashboard.js`'s undo/delete endpoints is now role-hardened but the mechanism itself is unchanged** — see §6a's backlog item #3. A real fix (per-user re-auth, a rotatable secret, or similar) needs actual design work, not attempted here. `transfer.js`'s and `outward.js`'s `POST /undo` no longer have this password at all (dropped by request on both) — they're role-gated only.

### Recently fixed (context only)

**`routes/po.js` had no error handling**, and neither did `routes/dashboard.js`, `routes/daily-gate.js`, or `utils/pdf.js` — an audit found the crash risk was broader than originally documented here. Any thrown error in an unwrapped async handler (e.g. a query against a `crm_*` table missing from the local SQLite fallback) was an unhandled rejection that **crashed the entire Node process**, taking down the app for every connected user, not just failing that one request. Fixed: `utils/asyncHandler.js` wraps every handler in those four files to forward errors to `next(err)`, and `server.js` gained a global Express error-handling middleware plus the `process.on('unhandledRejection', ...)` backstop mentioned above (which also covers the partial-coverage files noted above, just without the clean-response benefit).
